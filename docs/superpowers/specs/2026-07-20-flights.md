# Flights

**Status:** Current (as of 2026-07-27)
**Module:** `client/app/board/motion/flights.ts`, `client/app/board/motion/exit-fx.ts`, `client/app/board/motion/screen-motion.ts`, `client/app/board/bitmap/mount.ts`, `client/app/board/bitmap/paint-flights.ts`, `client/app/board/bitmap/paint-exit-fx.ts`, `client/app/board/bitmap/paint-screen-motion.ts`, `client/app/board/submodel.ts`, `client/app/board/messages.ts`

## Problem Statement

Playing, resolving, and moving cards must feel continuous without drawing duplicate cards or repainting the entire board every animation frame. Flights need to hide the resting source, retarget when authoritative game state arrives, settle cleanly, and respect reduced-motion preferences. Hand-drag, in-flight glides, and battlefield exit FX must share one screen-motion paint surface so drag→seed handoff does not jump between HTML and canvas.

## Solution

Screen motion on the board is Mount-painted on the flight layer. Three phases share that layer:

- **Dragging** — `DragGhost` from `motion/screen-motion.ts`, published on `BitmapFrame.dragGhost` while `handDrag` is active.
- **Flying** — `CardFlight` via `motion/flights.ts` (spawn / step / retarget / settle).
- **Exiting** — `ExitFx` via `motion/exit-fx.ts` (destroy / exile choreography).

`bitmap/paint-screen-motion.ts` paints drag, flights, then ExitFx on one pass. `bitmap/mount.ts` owns the animation clock for flying / exiting; drag poses update from Foldkit pointer messages without requiring rAF. `submodel.ts` still owns board Maps for `handDrag`, `flights`, and `exitFx` (paint is unified; model Maps stay split).

Design input: [`2026-07-27-unified-screen-motion-design.md`](2026-07-27-unified-screen-motion-design.md).

The full board layer stack lives in [`docs/client-canvas-map.md`](../../client-canvas-map.md). The flight / screen-motion layer is above hand and stack and above resting permanents.

## User Stories

- As a player, when I play a hand card, it travels from my hand toward the stack or battlefield without snapping.
- As a player, when a spell resolves, the card travels from the stack to its destination or disappears into the appropriate zone.
- As an opponent, I see played cards enter from the player area when there is no local hand ghost.
- As a player, when a permanent leaves the battlefield for the graveyard or exile, the board suppresses the generic glide and owns a short in-place exit effect at the last battlefield pose.
- As a reduced-motion user, I see state settle immediately without glide animation.

## Behavior

### Dragging (hand bar)

While the player drags a playable bar tile, the board publishes a `DragGhost` on the flight layer at the pointer (hand face scale via `handFlightScale`). The HTML hand bar fades the source tile and does **not** render a separate DOM ghost. The canvas ghost uses the shared lift shadow and zone playable strokes (mint ring; command / graveyard / exile outer outline). Mana-cost pips stay on resting bar tiles only — the ghost matches in-flight card paint so release→seed is continuous.

### Spawn

A flight is spawned when local action planning or synced game provenance identifies a card movement that should animate. Spawn records card id, optional source hand card id, print/name, screen-space start pose, screen-space target pose, scale, kind, and phase.

Common origins:

- Local hand drop starts from the drag release / hand tile screen origin (same pose as the drag ghost when dragging).
- Local activation menu or modal action can seed from the selected card or staged origin.
- Opponent plays start from that player's avatar when no local drag ghost exists.
- Stack resolve starts from the stack origin at stack scale.
- Battlefield exits do not spawn a `CardFlight`; they use the dedicated `ExitFx` orbit described below.

### Battlefield exit FX

Battlefield exit FX is a sibling orbit to `CardFlight`, not a special flight `kind`. Board sync only spawns `ExitFx` when `fold.provenance.battlefieldExits` marks a permanent as leaving the battlefield for the graveyard or exile:

- Battlefield -> graveyard spawns `kind: "destroy"`.
- Battlefield -> exile spawns `kind: "exile"`.
- Non-battlefield graveyard / exile moves keep the normal zone-move flight path.

Each effect starts at the permanent's most recent battlefield pose. If that id already owns a flight, sync samples the current flight pose, deletes the flight, and suppresses the generic zone-move / from-stack glide for the exiting id.

Choreography stays in place instead of gliding to the pile:

- Destroy: brief burn and ember rim, then an ash-collapse wipe over the lifted card face.
- Exile: shatter and shard breakup, then a cool void pinch that pulls the card inward and disappears it.

Board wipes start all eligible `ExitFx` in parallel. `particleAllowancePerFx` enforces the shared `EXIT_FX_MAX_PARTICLES` cap so large destroy / exile batches stay readable without saturating the flight canvas.

### Retarget

Flights do not invent zone moves. When a snapshot or delta produces the authoritative destination, the existing flight retargets to the card's current layout position or stack position. Retargeting preserves continuity and prevents a separate entrance animation for the same id.

Stack flights aim at the resting HTML stack face: `stackFaceScreenOrigin` (presentation-aware pile / strip / full) with `targetScale` from `stackLayout.STACK_CARD_W` (180). Seed and sync share that geometry so settle handoff does not jump from a stale mid-right / 112px pose.

Local hand seeds set `hold: true`. The Mount may park them as `phase: "settled"` at the aim pose, but `FlightsSynced` keeps held flights in the model so a later `stackEntrances` / `landPlayFrom` rebind continues the same flight — **except** when the flight id already names the resting destination (spell `source` on the stack, or permanent on the battlefield). In that post-rebind case, settle sync hands off immediately: keeping a settled held flight would leave a screen-space ghost that tracks the camera until the next provenance sync. Without hold, a seed that reaches the stack before provenance arrives is dropped and sync spawns a second flight from the avatar.

When sync finds a held local seed within `poseNearHandoff` (~72px / 0.25 scale) of the authoritative pose, it hands off immediately (flying or settled) instead of retargeting or continuing a stale seed glide. Continuing toward an outdated aim and correcting later is the short second animation. Far seeds retarget on one continuous flight and **retain `hold`**, so a later sync can hand off after settle. Stack HTML stays hidden for any in-model `kind: "stack"` flight, including the settled frame before `FlightsSynced` drops it.

Battlefield land seeds aim at a provisional lands-row center (`landRowCenter`) with battlefield scale so the card keeps moving from the drop toward the seat; `landPlayFrom` retargets while still far from the real slot (retaining hold) and hands off when parked on/near that slot.

Automatic `fitCamera` on game sync (and user wheel/pinch zoom) remaps live flight `scale` / `targetScale` by `oldZoom / newZoom` so on-screen size stays continuous — otherwise a parked stack seed drawn at the pre-fit zoom suddenly shrinks, then eases back up to `stackFlightScale(newZoom)` and reads as a second animation.

Land plays and stack moves may rebind a flight from source hand id to permanent id. The board keeps the source hand card hidden while the destination id owns the visible flight.

### Step and reduced motion

`stepFlights` advances screen pose and scale toward the target with the existing easing rules. If `prefers-reduced-motion: reduce` is active, flights snap to their targets and active `ExitFx` complete immediately without painting. Publish-time ExitFx payloads are stripped before the animated-layer paint and immediately synced back empty so reduced-motion users never see a one-frame battlefield exit effect. Settled flights stay in the sync payload long enough for the board model to clear ownership and hidden ids.

### Settle

A flight settles when it reaches the target pose or reduced motion forces the end state. On settle:

- The flight is removed from the live flying set.
- Held seeds still waiting for provenance stay in the model (see Retarget).
- Held flights whose id already matches the resting destination hand off on `FlightsSynced` so the resting face owns paint immediately.
- `hideCardIds` no longer hides the resting destination.
- `handHidden` releases the source hand tile when appropriate.
- The owned flight id set is updated so hand, stack, and bitmap paint can resume normal rendering.

Mixed payloads are valid: one `FlightsSynced` message may retain still-flying entries while dropping settled entries.

### Visibility and ownership

`hideCardIds` suppresses resting battlefield faces (bitmap) for ids currently flying and for ids owned by active `ExitFx` so the card never shows both as a resting permanent and as an exit animation. The stack overlay hides a resting face only when a flight with `kind: "stack"` owns that object id — so a battlefield / from-stack flight for an ability's source permanent does not blank the ability face. `handHidden` suppresses source hand tiles. The flight-owned id invariant, exposed in the model as `ownedIds` and conceptually as `flightOwnedIds`, prevents competing HTML entrances and duplicate resting faces while a flight owns a card id.

### Paint layer

`board-flight-layer` is a pointer-events-none canvas above hand and stack. `paintScreenMotion` draws the active drag ghost (if any), each live flight, and ExitFx on that layer. Resting permanents remain on `board-bitmap-layer`.

- Drag ghosts and in-flight cards use the shared lift shadow (`LIFT_SHADOW_*` / `FLIGHT_SHADOW_*` from `lift-shadow.ts` → `paint-flights.ts`): `shadowOffsetY` 16, `shadowBlur` 36, `rgba(0,0,0,0.72)`, matching `--drop-shadow-drag`. Resting hand tiles stay on `--shadow-hand`. Drag ghosts add zone playable strokes; plain flights do not.

### Mount-local animation

The flight Mount owns `requestAnimationFrame` while live flights exist. Each frame:

1. Step flight poses locally.
2. Paint the flight layer only, including any active `ExitFx`.
3. Emit `FlightsSynced` only when flying membership changes, all flights settle, `ExitFx` membership changes, or reduced-motion publish collapses `ExitFx` immediately. Exit-FX progress-only pose ticks stay Mount-local. The payload carries the current `exitFx` membership so battlefield-exit hiding survives flight-clock syncs and clears synchronously when reduced motion bypasses the effect.

Pose-only frames do not run a full board update, do not rebuild `Canvas.view`, and do not repaint the resting bitmap layer.

### Paint gating

`publishBitmapFrame` compares non-flight frame inputs through a resting paint snapshot. Resting bitmap repaint happens when layout, camera, selection, targets, combat staging, payment preview, actions, or hide sets change. Flight pose ticks repaint only the flight layer. Spawn, retarget, and settle still publish normal model state so ownership and hidden ids stay correct.

## Implementation Decisions

- Keep flight math pure in `motion/flights.ts` and DOM-free; drag poses convert via `motion/screen-motion.ts`.
- Keep the animation clock inside the flight Mount for flying / exiting; drag poses republish from Foldkit pointer messages.
- Paint drag, flights, and ExitFx through one `paintScreenMotion` pass on the flight layer.
- Keep resting paint gated separately from flight pose / drag paint.
- Keep all zone movement authority in game sync and action results; the Mount only animates authorized poses (plus the local drag ghost).
- Keep reduced-motion behavior equivalent to immediate settle.
- Keep `hideCardIds`, `handHidden`, and flight-owned ids as the duplicate-rendering guards.
- Keep `BoardModel.handDrag` / `flights` / `exitFx` as separate Maps for now; paint ownership is unified first.

## Testing Decisions

- `client/app/board/motion/screen-motion.test.ts` covers `dragGhostFromHandDrag` pose/scale.
- `client/app/board/bitmap/paint-screen-motion.test.ts` covers drag ghost lift shadow and zone strokes on the shared flight layer.
- Hand unit/Scene tests assert drag source fade without an HTML `hand-drag-ghost`.
- `client/app/board/motion/exit-fx.test.ts` covers ExitFx spawn, progress/completion, reduced-motion completion, shared particle budgeting, and per-kind palettes.
- `client/app/board/exit-fx-sync.test.ts` covers battlefield -> graveyard / exile triggers, glide suppression, current-flight pose sampling, id rebinds, and `hideCardIds`.
- `client/app/board/bitmap/paint-exit-fx.test.ts` covers destroy ember paint and exile squash / void paint on the shared flight layer.
- Bitmap frame tests assert pose-only ticks skip resting paint and repaint only the flight layer, and that reduced-motion publish strips ExitFx before the animated-layer paint.
- Story/update tests assert `FlightsSynced` keeps flying ids hidden, clears settled ids, preserves exit-FX hidden ids, and that `syncBoardWithGame` spawns destroy / exile exit FX while suppressing battlefield-exit glides.
- `client/app/board/flight-stack-aim.test.ts` asserts stack flight scale matches the resting HTML face width, that `syncBoardWithGame` retargets stack entrance flights to `stackFaceScreenOrigin`, that parked held seeds hand off without correction glides (including slight face drift and auto camera-fit), that land seeds aim at the lands row so they keep moving until sync, and that `FlightsSynced` hands off settled held flights once authority owns the destination while retaining pre-rebind seeds.
- Scene tests assert hand faces are suppressed while the flight owns the id; stack faces are suppressed only for `kind: "stack"` flights.

## Out of Scope

- Changing non-exit flight visual design beyond lift-shadow polish and timing/pose parity.
- WebGL, OffscreenCanvas, workers, Pixi, or dirty-rect systems.
- Pointer-move throttling unrelated to active flights.
- Changing engine zone movement or payment semantics.
